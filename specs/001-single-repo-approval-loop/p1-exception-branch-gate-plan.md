## 1. 门禁声明（Gate-G-P1，即日生效）

**在本文件 §3 的三项离线验证（FS2a/FS2b/FS2c）全部执行并通过、并经
人工验收登记之前，不得开始任何真实 AI 调用（含 FV-1 及其后各项），
不得安装 Agent SDK 或发起付费调用。**

| 分支 | 触发面 | 当前状态 |
|---|---|---|
| G1 Git 命令异常 | 任一 `git … \|\| cell_verdict "F<n>" "fail" "git cmd failed: …"` | **未验证** |
| G2 证据缺失 | `require_evid`（证据文件不存在/空） | **未验证** |
| G3 判定器错误 | `do_diff` 返回 90（分类器内部命令失败） | **未验证** |

已实测部分（不得外推至上述分支）：P1 主路径——真实判定失败
（V2 首次 FS1）与故意判定失败（V2.1 FS1 受控重试）均已验证
STOP + exit 3 + 后续格零产物 + 收尾证据保存。

## 2. 为何是 AI 调用前门禁

FV-1 起将产生真实调用与费用。失败即停是费用与安全边界的最后一道
本地闸（触顶/异常即停、不自行修复重试）。三条异常分支未实测意味着
「异常时熔断是否真实生效」尚无证据；在取得证据前开放付费调用，
违反证据优先原则（AGENTS.md §5）与费用双控精神（附录 A 细节-4）。

## 3. FS2 最小离线验证方案（设计；执行须单独授权）

**性质**：与 FS1 同类的合成自检——故意制造**合法异常**（预期判定 =
fail → 熔断），验证的是**停止行为**，不是 Git 语义。零网络、零安装、
零 AI、纯离线合成。三个场景相互独立，各自单次执行、独立留证。

### 3.1 实现载体

新建独立自检脚本 `run-p1-fs2.sh`（不修改 run-fv0-v2.2.sh 及任何既有
脚本/证据）；从 v2.2 复用 `fail_stop` / `cell_verdict` / `require_evid` /
`do_diff` 函数体（复制并标注来源哈希 `f00f9cb5…`），或 source 其
函数段——以 diff 可核对的最小方式实现，判定语义零改动。

### 3.2 场景设计

| 场景 | 注入方式 | **触发来源归属（必须核验）** | 预期行为 |
|---|---|---|---|
| FS2a Git 命令异常 | 合成仓库上执行必然失败的 git 命令（如 `git show HEAD:nonexistent-file`）经 `\|\| cell_verdict fail "git cmd failed"` 路径 | STOP 原因必须是**注入的那条 git 命令**失败（`git cmd failed: <注入命令>` 逐字对应），而非其他格的判定 fail | 熔断 |
| FS2b 证据缺失 | `require_evid` 指向不存在文件；第二子场景指向空文件（0 字节） | STOP 原因必须为 `evidence missing or empty: <注入路径>`（逐字对应），且该路径确为注入目标 | 熔断 |
| FS2c 判定器错误 | 构造使 `do_diff` 内部命令失败的输入（如在分类前使其依赖的 `git ls-tree`/`archive` 对不可读仓库执行），使 `do_diff` 返回 90 | STOP 原因必须为判定器错误语义（`diff_unclassified=90`/判定器错误），且 `do_diff` 返回值 90 有独立留证，不得以普通未归类差异（返回 N>0）冒充 | 熔断 |

### 3.3 执行控制（每场景必遵）

1. **独立 TEMP 执行根**：每个场景（FS2a/2b/2c，及 FS2b 的两子场景）
   各用**全新独立** `%TEMP%` 子目录，互不复用；各自通过原路径安全
   门禁（TEMP 白名单、ReparsePoint 探针、`assert_in_root`）+ Git
   环境净化，留各自门禁证据。
2. **通用验收清单（逐场景逐项核，缺一即该场景不通过）**：
   ①STOP 行存在且**触发来源归属正确**（§3.2 表）；
   ②实际退出码 = 3；
   ③STOP 之后**后续步骤零执行**（后续格证据计数 = 0，mtime 不晚于
   收尾件）；
   ④**安全收尾完整**：after-status + 前后 diff、inventory、summary
   均保存（熔断路径收尾顺序①②③④成立）；
   ⑤写入全部位于本场景执行根内；⑥无清理动作。
3. **误判防护（不允许其他提前失败冒充通过）**：
   - 合格的通过要求**注入点之前的所有准备步骤全部成功**（准备步骤
     逐项留证：fixture 构建、基线格 pass 等）；注入的异常必须是
     **首个失败**。
   - 若在注入点之前发生任何其他失败（fixture 构建失败、门禁失败、
     基线格 fail 等）并提前触发熔断：该场景判 **INVALID（不通过）**，
     **不得**因「出现了 STOP + exit 3」而误判为通过；如实登记实际
     触发来源，停止，不自行修复重试。
   - 判读三要素同时满足才可判通过：STOP 原因逐字归属正确 + 准备
     步骤全绿 + 退出码 3 且收尾完整。
4. 每场景仅执行一次；任何失败（含 INVALID）→ 停止、登记、不自行
   修复重试（与 FS1 纪律一致）。

### 3.4 失败判定（自检不通过 = P1 异常分支修复不合格）

- 任一场景未触发熔断、或退出码 ≠ 3、或无 STOP 行、或 STOP 触发
  来源归属错误、或缺收尾证据、或后续格产生产物、或命中 §3.3-3 的
  INVALID 条件 → 该分支判**未通过**，登记结果、停止、不自行修复。

### 3.5 执行约束（届时适用）

零网络、零安装、零 AI；仅新执行根内写入；不触碰任何既有档案
（FV-0/V2/V2.1/V2.2 证据）；不触碰真实仓库写面；执行**须用户单独
授权**（本文件仅设计）；结果独立登记，通过后方可解除 §1 门禁。
