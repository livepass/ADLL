## 产品目标与非目标

**目标（V1.1 必须交付）**

- 建立「关联仓库 → 创建任务 → 真实 AI 生成技术方案 → 版本化修改 →
  人工批准/驳回 → 记录留存」的单轮可信闭环，全程网页操作。
- 任务、方案版本、审批记录的基本持久化与重启恢复是必须交付的核心能力。
- 方案生成与审批严格绑定 Git 基准（完整 commit SHA），形成可追溯、
  可审计、可恢复的审批证据链。
- 只读性由真实权限约束与可验证证据保证，而非提示词。
- AI 方案具备证据优先的依据说明（真实源码、来源引用、事实/假设/推测区分）。

**非目标（V1.1 明确不做）**

- 不实现实际 AI 编码与自动化测试执行（属 V1.2）。
- 不接入 Obsidian Vault、知识卡、教学问答（属 V1.3）。
- 不做多 Agent 调度与多执行器实例（仅预留可扩展接口）。
- 不做复杂项目管理中心、批量任务、跨设备与多人协作。
- 不构建独立的论文检索或 GitHub 研究平台（证据能力仅内嵌于方案生成）。
- 不 Fork OpenHands / Dify，不将 LangGraph 引入依赖（技术边界见 Requirements）。

## Clarifications

### Session 2026-10-17

- Q: 用户是否可以通过网页修改已创建任务的需求描述，且每次正式修改都生成
  不可变的新需求版本、旧审批不自动继承？ →
  A: 采用方案 A——允许修改；仅在用户**正式保存并提交**需求修改时创建新的
  不可变需求版本（编辑草稿变化不触发版本创建）；新需求版本不自动继承旧
  审批，必须按现有审批门禁重新审批；历史需求版本、技术方案与审批事件
  完整保留，不得覆盖或删除；旧审批事件本身不变，但不作为新需求版本的
  有效审批凭证。
- Q: 生成进程崩溃/强制退出/应用重启导致完整性核验未完成时，是否标记
  「未确认」、禁止以「已验证」状态进入审批，并允许恢复后补充核验？ →
  A: 采用方案 A 并附加约束——①核验未完成必须标记「未确认」，禁止以
  已验证状态进入审批；②恢复后补充核验必须具备可信的生成前基准、原分析
  快照、执行记录及足够的权限隔离证据；③证据不足或无法确认原生成完整
  完成时，不得仅凭恢复后文件哈希一致判定通过，保持「未确认」或标记
  核验失败并要求重新生成；④必须区分「生成执行状态」「完整性核验状态」
  「人工审批状态」，核验成功不等于人工批准；⑤已取消/失败/超时且未产生
  可信完整结果的生成，不得通过事后补充核验恢复为成功方案；⑥历史生成
  记录、核验结果与失败原因必须保留，不得覆盖原始证据。完整性检查与
  隔离的具体实现留待技术规划。
- Q: 原仓库 HEAD 自然变化是否与用户主动更换任务分析基准区别处理
 （HEAD 不自动更改绑定 Commit，主动更换须重新审批）？ →
  A: 采用方案 A 并附加规则——①任务绑定的完整 Commit SHA 是固定分析
  基准，HEAD 自然变化不得自动改变绑定 Commit，也不得仅因此使现有审批
  失效；②用户主动更换分析基准属于分析对象变更，必须创建新的分析基准
  记录、重新分析并生成对应方案，新方案不得继承旧审批；③历史方案、
  历史审批事件及其原始 Git 基准必须保留，不得覆盖；④原绑定 Commit
  不可访问、丢失或无法验证身份时，标记基准不可用，阻止依赖该基准的
  生成与新审批，不得自动回退到当前 HEAD；⑤工作区未提交/未跟踪修改
  不得自动混入固定 Commit 的分析内容。Git 快照保存、对象保留与工作区
  隔离的具体实现方式留待技术规划。
- Q: 向外部 AI 服务发送源码前，默认授权范围与敏感文件排除应采用哪种
  规则，且必须由用户知情确认？ →
  A: 采用方案 A 并附加要求——①默认排除敏感文件、密钥、环境配置及
  高风险内容，发送范围遵循最小必要原则（仅任务相关且已授权的项目
  源码）；②发送前必须说明接收方、拟发送数据类型与具体授权范围并
  取得明确确认；③授权范围必须可核查，记录授权范围及其对应的任务
  与分析基准以供审计；④不得擅自扩大范围，超出原授权范围须重新确认；
  ⑤敏感排除规则不是绝对安全保证（普通源码亦可能含密钥），仍受敏感
  信息保护条款约束；⑥用户取消授权或拒绝发送时不得继续发送，并明确
  告知生成受阻原因；⑦不要求每次生成逐文件勾选，同任务、分析基准与
  授权范围未变时可复用有效授权，但必须提供查看与撤销方式；⑧文件
  选择界面、敏感信息检测技术与授权存储方式留待技术规划。
- Q: V1.1 对外部 AI 调用的费用与限额信息，是否只展示可获得的失败、限额
  与费用内容，不建设完整用量面板？ →
  A: 采用方案 A 并附加要求——①仅展示实际可获得的失败原因、限额、
  Token 用量及费用信息，不建设完整用量统计面板；②必须区分服务商
  返回的实际用量/费用、根据可用数据计算的估算费用、无法获得的费用
  信息三类；③无法获取时必须明确标注未知或不可用，不得编造金额，
  也不得默认视为免费；④API 认证方式、计费条件、调用限制及费用获取
  能力在技术规划阶段通过受控可行性测试验证；⑤不实现历史费用汇总、
  费用图表、预算管理或复杂成本监控；⑥调用日志、错误提示与费用信息
  不得泄露 API Key、Token 等敏感凭据。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 关联授权仓库并创建开发任务 (Priority: P1)

用户在网页中授权并关联一个本地 Git 示例项目，系统展示该仓库当前分支、
完整 commit SHA 与工作区状态。若存在未提交或未跟踪更改，系统显式提示，
用户必须选择处理方式后才能创建开发任务并继续。系统只以绑定 commit 的
源码快照为分析基准，绝不擅自清理、删除或覆盖用户工作区的任何修改。

**Why this priority**: 一切分析与审批都锚定在可信 Git 基准上；
基准不可信则后续方案与审批全部失效。

**Independent Test**: 关联一个含脏更改的仓库，验证系统显式提示、
阻止静默混入且不触碰工作区文件；确认基准后可成功创建任务并显示绑定的
完整 SHA。

**Acceptance Scenarios**:

1. **Given** 用户持有一个本地 Git 仓库路径，**When** 在网页中授权关联，
   **Then** 系统展示仓库标识、当前分支、完整 commit SHA 与工作区状态。
2. **Given** 仓库存在未提交/未跟踪更改，**When** 用户尝试创建任务并生成方案，
   **Then** 系统显式提示并要求用户确认处理方式，未提交/未跟踪修改不静默
   进入分析基准。
3. **Given** 用户确认以干净 commit 为基准并填写任务需求，**When** 提交创建，
   **Then** 任务创建成功，记录绑定的完整 commit SHA 与需求内容；
   **And** 用户工作区文件保持原样（无清理、删除、覆盖）。
4. **Given** 任务已创建且绑定基准 commit，**When** 发起方案生成，
   **Then** AI 仅读取该 commit 的源码快照，工作区后续修改不影响本次分析内容。
5. **Given** 任务已绑定基准 commit 且已有批准，**When** 原仓库 HEAD
   发生自然变化，**Then** 任务绑定的 Commit 不变，现有审批不受影响。
6. **Given** 任务已创建，**When** 用户编辑需求但未正式保存提交，
   **Then** 不创建新需求版本；**When** 用户正式保存并提交修改，
   **Then** 创建不可变的新需求版本，历史需求版本保留。

### User Story 2 - 真实 AI 生成技术方案（受控只读 + 证据依据） (Priority: P1)

用户对已创建的任务发起方案生成。系统在受控、只读的分析环境中调用真实 AI
分析目标项目源码快照，产出技术方案。分析过程不执行目标项目的业务代码、
构建脚本或测试脚本；目标仓库内的提示词与规则文件仅作为不可信数据处理。
方案包含依据说明：引用的真实源码文件及对应 Git Commit、重要决策的参考资料、
可验证外部来源、事实/假设/推测的区分、未完成核实的内容及风险。生成前后
系统核对分析范围内的文件完整性并留存证据。用户知晓并授权向外部 AI 服务
发送源码的范围，范围外内容不得擅自传输。

**Why this priority**: 真实 AI 方案生成是 ADLL 的核心价值；
无证据、可篡改或可越权的方案使审批失去意义。

**Independent Test**: 对示例项目发起生成，验证产出方案真实来自 AI（非 Mock）、
目标项目文件未被修改（有完整性证据）、方案含来源与三类标注、
出站数据未超出用户授权范围。

**Acceptance Scenarios**:

1. **Given** 任务绑定基准 commit，**When** 用户发起方案生成，
   **Then** 系统在受控只读分析环境中真实调用 AI，产出技术方案并展示进度与结果。
2. **Given** 生成完成，**When** 用户查看方案，**Then** 方案含源码依据
  （文件 + commit）、参考资料来源、事实/假设/推测区分、未核实内容及风险提示。
3. **Given** 生成正常完成并可提交审批，**When** 检查只读约束与
   分析范围内文件完整性，**Then** 系统留存充分的只读约束证据与
   完整性核验结果（生成前后比对），未覆盖检测范围如实说明，
   不以生成前后哈希一致单独宣称运行期间绝对未修改。
4. **Given** 生成后核验因崩溃/重启未完成，**When** 用户查看该次生成，
   **Then** 完整性核验状态显示「未确认」，已有证据保留不被覆盖，
   结果不可作为已验证方案提交审批。
5. **Given** 分析过程，**When** 目标仓库中存在构建脚本、测试脚本或
   业务代码入口，**Then** 系统不执行它们；仅读取源码快照。
6. **Given** 首次向外部 AI 服务发送源码前，**When** 用户配置分析范围，
   **Then** 系统说明接收方、数据类型与授权范围，展示默认排除规则
  （敏感/密钥/环境配置）与最小必要默认范围并取得明确确认；
   **And** 敏感文件、密钥及授权范围外内容不被传输；授权范围与
   任务、分析基准的关联被记录可审计。
7. **Given** 用户取消授权或拒绝发送，**When** 系统准备发送源码，
   **Then** 不向外部 AI 服务发送，生成受阻并明确告知原因；
   **When** 后续分析需要原授权范围之外的内容，
   **Then** 重新请求确认，未确认前不扩大发送范围。
8. **Given** AI 无法访问外部资料，**When** 生成方案，
   **Then** 方案中明确说明"未能访问/未验证"，不得伪称已搜索或已验证。
9. **Given** 同一任务、同一分析基准下再次生成，且外部 AI 接收方、
   实际发送范围与授权有效状态均未变化，**When** 复用既有授权，
   **Then** 无需逐文件重新勾选，仍可查看与撤销授权；
   复用前提任一不成立时不得复用。
10. **Given** 生成需要更换外部 AI 接收方或扩大实际发送范围，
   **When** 发起发送，**Then** 系统重新取得用户的明确授权，
   未重新授权前不发送任何内容。

### User Story 3 - 审阅方案、提交修改意见、生成新版本 (Priority: P2)

用户查看方案版本，提交修改意见；系统保留旧版本并生成新版方案，
形成完整版本链。每次正式方案内容修改都创建新版本。用户可查看各版本
差异摘要、意见记录与生成状态。新版本不自动继承上一版本的审批。

**Why this priority**: 方案需要人机迭代；版本链是审批可追溯的基础。

**Independent Test**: 对方案提交两次修改意见，验证生成两个新版本、
旧版本全部保留、版本链与意见记录可查看。

**Acceptance Scenarios**:

1. **Given** 存在方案版本 v1，**When** 用户提交修改意见并要求重新生成，
   **Then** 生成 v2，v1 完整保留，版本链与意见记录可查看。
2. **Given** 重新生成失败，**When** 用户查看状态，
   **Then** 显示真实失败状态与原因，旧版本不受影响，可再次发起。

---

### User Story 4 - 人工批准或驳回方案（绑定要素齐全） (Priority: P1)

用户对某一方案版本做出明确的批准或驳回决定。审批事件绑定任务需求版本、
仓库关联身份、完整 Git Commit SHA、方案版本与内容摘要，事件一旦记录
不可变。审批「是否仍然有效」单独判定：每次正式方案内容修改生成的新版本
均不继承上一版本审批；需求版本或分析基准发生变化时，旧审批不得自动复用。
系统防止重复批准。Agent 不得以"仅属措辞修改"为由绕过新版本审批，
审批门禁由服务端强制，任何绕过尝试都会被拒绝并记录。

**Why this priority**: 审批是不可协商的信任门禁（宪章原则 III）；
缺失则整个闭环不成立，与任务、生成同属 P1 核心。

**Independent Test**: 批准 v1 后生成 v2，验证 v2 无有效审批且 v1 审批
事件保留；对同一版本重复/并发批准，验证被拒绝；模拟 Agent 绕过服务端
门禁，验证被拒绝并记录。

**Acceptance Scenarios**:

1. **Given** 方案版本待批准，**When** 用户明确批准，
   **Then** 生成不可变审批事件，绑定需求版本、仓库关联身份、完整 commit SHA、
   方案版本与内容摘要。
2. **Given** v1 已批准且当前有效，**When** 因修改意见生成 v2，
   **Then** v2 不继承 v1 审批（当前无有效审批，须重新批准），
   **And** v1 的审批事件保留可查。
3. **Given** 某方案已批准，**When** 需求版本或分析基准发生变化，
   **Then** 该审批的当前有效性判定为失效、不得自动复用，须重新审批；
   历史审批事件保留。
4. **Given** 同一方案版本已批准或批准进行中，**When** 重复或并发发起批准，
   **Then** 仅产生一条有效批准记录，其余被拒绝并记录。
5. **Given** 用户驳回方案，**When** 操作完成，
   **Then** 记录驳回及理由，任务回到可继续迭代状态。
6. **Given** Agent 或自动化组件尝试直接写入批准状态或绕过服务端审批门禁，
   **When** 请求到达服务端，
   **Then** 被拒绝、不产生审批效果，并作为安全事件记录。
7. **Given** 任务需求版本 v1 已批准，**When** 用户正式保存需求修改生成 v2，
   **Then** v2 不可变且不继承 v1 审批（须按审批门禁重新审批），
   **And** v1 需求版本与 v1 审批事件均完整保留、不被覆盖或删除。
8. **Given** 某次生成的完整性核验状态为「未确认」，**When** 尝试将其结果
   提交审批，**Then** 被拒绝，不得以已验证状态进入审批。
9. **Given** 任务已有批准，**When** 用户主动更换分析基准，
   **Then** 创建新的分析基准记录、重新分析并生成对应方案，
   **And** 新方案不继承旧审批（须重新审批），历史方案、审批事件及其
   原始 Git 基准完整保留。

---

### User Story 5 - 失败、取消与恢复追溯 (Priority: P2)

生成失败、超时、用户取消或重试时，系统展示真实执行状态（执行 ID、
当前状态、失败/取消结果、可重试动作）。用户可请求取消正在运行的方案生成，
系统如实报告实际取消结果。取消后迟到的生成结果不得覆盖已有方案版本、
不得产生隐式批准。取消与失败历史全部保留。页面刷新或应用重启后，
任务、方案版本、审批记录与失败/取消历史均可恢复查看。

**Why this priority**: 真实 AI 调用必然伴随失败与中断；任务、方案、
审批记录的基本持久化与重启恢复是 V1.1 必须交付的核心能力。

**Independent Test**: 模拟生成超时后重试、发起取消并验证真实取消结果与
无迟到覆盖；重启应用后验证全部历史可恢复。

**Acceptance Scenarios**:

1. **Given** 生成超时或失败，**When** 用户查看任务，
   **Then** 显示真实执行 ID、失败原因与可用重试动作。
2. **Given** 生成正在运行，**When** 用户请求取消，
   **Then** 系统执行取消并明确报告实际结果（如已取消/未能取消/结果已产生
   等真实状态），不虚假声称已取消。
3. **Given** 生成已被取消，**When** 迟到的生成结果随后到达，
   **Then** 该结果被丢弃并记录，不覆盖已有方案版本，不产生任何隐式批准。
4. **Given** 失败后重试成功，**When** 检查记录，
   **Then** 新执行记录追加保存，失败/取消历史保留，无版本覆盖、无重复批准。
5. **Given** 页面刷新或应用重启，**When** 用户重新进入，
   **Then** 任务、方案版本、审批记录与失败/取消历史完整可恢复；
   中断的生成按可验证状态定义呈现（见 FR-037），可安全重试。
6. **Given** 中断后恢复并尝试补充核验，**When** 证据不足或无法确认
   原生成完整完成（即使文件哈希一致），**Then** 保持「未确认」或标记
   核验失败并要求重新生成，不得判定核验通过。
7. **Given** 一次外部 AI 调用完成或失败，**When** 用户查看执行详情，
   **Then** 显示实际可获得的失败原因、限额、Token 用量及费用信息；
   费用区分「实际/估算/未知」三类，未知明确标注不可用，
   不出现编造金额或默认免费。

---

### Edge Cases

- 仓库路径无效、非 Git 仓库、无读取授权：关联失败并给出可操作提示，不创建任务。
- 分析基准 commit 在仓库中被改写/丢失/无法验证身份：标记基准不可用，
  阻止生成与新审批，不自动回退到当前 HEAD。
- 并发重复点击"生成"或"批准"：以幂等与状态锁保证只产生一次有效结果。
- 取消请求与自然完成竞态：以真实最终状态为准，如实报告；迟到结果按
  丢弃处理。
- AI 输出为空、格式异常或明显未按要求：按生成失败处理，展示真实原因。
- 目标仓库内容含提示注入指令（README/注释/规则文件）：一律视为不可信数据，
  不得诱导越权写文件、执行业务代码/构建脚本/测试脚本或绕过审批门禁；
  发生即为阻断级缺陷。
- 敏感信息（密钥、令牌）出现在分析内容中：不得写入日志、方案明文，
  不得未经授权向外部 AI 服务传输。
- 普通源码文件中夹带密钥（超出敏感排除规则覆盖）：排除规则不作为
  绝对安全保证，按敏感信息保护要求处理。
- 分析中途需要读取原授权范围之外的文件：重新请求用户确认，
  未确认前不发送、不读取。
- Agent 尝试绕过人工审批服务端门禁（直接写状态、伪造批准记录）：
  必须被拒绝并记录为安全事件。
- 恢复后文件哈希一致但缺少生成前基准/快照/执行记录等证据：
  不得判定核验通过，保持「未确认」或标记核验失败。

## Requirements *(mandatory)*

### Functional Requirements

**仓库关联与 Git 基准**

- **FR-001**: 系统 MUST 支持用户通过网页授权并关联一个本地 Git 仓库作为
  分析目标；V1.1 仅支持一个活跃关联目标。
- **FR-002**: 系统 MUST 展示并记录关联仓库的仓库关联身份、完整 commit SHA、
  分支与工作区状态；方案与审批 MUST 绑定完整 commit SHA（非缩写）。
  任务绑定的完整 Commit SHA 是固定分析基准：原仓库 HEAD 自然变化
  MUST NOT 自动改变任务绑定的 Commit，也 MUST NOT 仅因此使现有审批失效。
- **FR-003**: 当工作区存在未提交或未跟踪更改时，系统 MUST 显式提示并
  要求用户选择处理方式；MUST NOT 将脏更改静默混入分析基准。
- **FR-004**: 未经授权的路径、非 Git 仓库或不可读目录，系统 MUST 拒绝关联
  并给出明确错误。
- **FR-005**: AI 分析 MUST 仅针对明确绑定的 Git Commit 源码快照；
  未提交与未跟踪的修改 MUST NOT 进入分析内容，也 MUST NOT 自动混入
  固定 Commit 的分析基准。
- **FR-006**: 系统 MUST NOT 擅自清理、删除或覆盖用户工作区的修改。

**任务管理**

- **FR-007**: 用户 MUST 能通过网页创建、查看并修改开发任务的需求描述；
  仅在用户正式保存并提交修改时 MUST 创建新的不可变需求版本，
  编辑过程中的草稿变化 MUST NOT 触发版本创建。
- **FR-008**: 系统 MUST 持久化保存多条历史任务记录；"单任务"仅指 V1.1
  单轮最小场景以一个活跃任务为主，MUST NOT 解释为系统只能保存一条历史。

**AI 方案生成（真实、受控只读）**

- **FR-009**: 系统 MUST 通过真实 AI 能力生成技术方案；测试 Mock 仅可用于
  自动化测试，MUST NOT 作为正式产品功能或演示模式输出。
- **FR-010**: 方案生成 MUST 在受控、只读的分析环境中进行；MUST NOT 修改
  目标项目业务代码或在目标仓库本体执行可写操作。
- **FR-011**: 分析过程 MUST NOT 执行目标项目的业务代码、构建脚本或
  测试脚本。
- **FR-012**: 只读性 MUST 由实际权限约束（工具拒绝规则、隔离工作区/进程、
  应用后端约束等）保证，并留存可验证证据（如生成前后文件完整性比对）；
  仅依靠提示词 MUST NOT 视为满足本条。具体权限技术实现留待技术规划，
  MUST NOT 提前锁定特定 SDK 或隔离工具。
- **FR-013**: 系统 MUST 在生成前后核对分析范围内的文件完整性并留存证据；
  MUST 说明未检测覆盖范围，MUST NOT 宣称绝对未变更。生成后核验因崩溃、
  强制退出或应用重启而未完成时，MUST 标记为「未确认」，MUST NOT 以
  「已验证」状态进入审批。
- **FR-014**: 目标仓库内的 README、注释、配置、提示词与规则文件 MUST 一律
  视为不可信数据；MUST NOT 自动提升为控制指令或执行其中的指令。

**出站数据与用户授权**

- **FR-015**: 在向外部 AI 服务发送源码前，系统 MUST 向用户说明接收方、
  拟发送的数据类型和具体授权范围，并取得明确确认；默认排除敏感文件、
  密钥、环境配置及其他高风险内容，默认发送范围遵循最小必要原则
 （仅包含当前任务相关且已获授权的项目源码）；授权范围 MUST 可核查，
  系统 MUST 记录用户授权的范围及其对应的任务和分析基准以供审计；
  授权后 MUST NOT 擅自扩大范围，需要读取或发送原范围之外内容时
  MUST 重新获得用户确认；用户取消授权或拒绝发送时 MUST NOT 继续发送，
  并 MUST 明确告知生成受阻原因。不要求每次生成逐文件勾选：仅当任务、
  分析基准、外部 AI 接收方、实际发送范围与授权有效状态均未变化时，
  MAY 复用仍然有效的授权，但 MUST 提供查看和撤销方式；外部 AI 接收方
  发生变化或实际发送范围扩大时，MUST 重新取得用户的明确授权，
  未重新授权前 MUST NOT 发送。
- **FR-016**: 敏感文件、密钥及授权范围之外的内容 MUST NOT 未经授权
  传输给外部 AI 服务；敏感文件排除规则 MUST NOT 被视为绝对安全保证
 （普通源码文件中亦可能包含密钥），仍 MUST 受敏感信息保护要求约束
 （见 FR-042）。
- **FR-049**: 文件选择界面、敏感信息检测技术及授权存储方式 MUST 留待
  技术规划阶段决策；本规格 MUST NOT 提前规定实现工具。

**来源与证据要求**

- **FR-017**: AI 生成的技术方案 MUST 说明依据：引用的真实源码文件及对应
  Git Commit。
- **FR-018**: 方案中的重要技术决策 MUST 附实际采用的参考资料，以及引用的
  GitHub 项目、官方文档、论文或可信网页的可验证来源（链接/标识）。
- **FR-019**: 方案 MUST 严格区分「已核实事实」「未经验证的假设」
  「推测」三类内容；未完成核实的内容 MUST 明示并说明潜在风险。
  某一类别确实不存在相关内容时 MAY 明确标注「无」，MUST NOT 强行编造。
- **FR-020**: 面对复杂技术选型、架构设计与非平凡问题，方案生成 SHOULD
  优先利用项目已有调研记录与能够真实访问的可靠资料，并比较适用性、
  复杂度、维护成本、安全性与许可证。
- **FR-021**: 外部检索不可用时，方案 MAY 引用已核实的项目内资料，
  但 MUST 明确披露外部核查未完成；MUST NOT 伪称已搜索或已验证。
- **FR-022**: 方案 MUST NOT 编造来源；对不存在依据的推测 MUST NOT
  强行编造内容，宁可标注「无」或留空并说明。
- **FR-023**: 对版本敏感的外部结论（API 行为、许可证、安全公告等），
  方案 MUST 注明核查时间；采用前 MUST 可重新核实。
- **FR-024**: 调研报告中的候选技术（如候选 SDK、框架）MUST NOT 直接
  变成最终选型；选型 MUST 经技术规划阶段验证与 ADR 批准。

**版本与修改意见**

- **FR-025**: 用户 MUST 能查看方案版本、提交修改意见并触发生成新版本；
  旧版本 MUST 完整保留，形成版本链。
- **FR-026**: 每次正式方案内容修改 MUST 创建新版本；系统 MUST 记录每次
  生成的执行 ID、状态、结果与失败/取消原因。

**核心状态与审批行为**

- **FR-027**: 任务、方案生成、审批 MUST 具备明确状态机，非法状态流转
  MUST 被拒绝并记录（后端强制校验）；生成状态机 MUST 包含可验证的
  中断状态（如运行中/已完成/已失败/超时/已取消/迟到结果已丢弃）。
- **FR-028**: 审批事件 MUST 绑定五个要素：任务需求版本、仓库关联身份、
  完整 Git Commit SHA、方案版本、方案内容摘要；审批事件记录后 MUST
  不可变。
- **FR-029**: 审批「当前是否有效」MUST 与历史事件分离、单独判定：
  新版本方案 MUST NOT 自动继承上一版本的审批；需求版本或分析基准
  发生变化时，旧审批 MUST NOT 自动复用，须按现有审批门禁重新审批；
  旧审批事件本身 MUST 保持不变，但 MUST NOT 作为新需求版本或新方案
  版本的有效审批凭证。用户主动更换分析基准时，MUST 创建新的分析
  基准记录，重新分析并生成对应方案；新方案 MUST NOT 继承旧审批。
- **FR-030**: 任何正式方案内容修改都 MUST 走新版本 + 重新审批；
  MUST NOT 由 Agent 自主判断"仅属措辞修改"而绕过新版本审批。
- **FR-031**: 系统 MUST 防止重复批准：对同一有效审批对象的重复批准、
  并发批准 MUST 只产生一条有效批准记录，其余被拒绝并记录。
- **FR-032**: 用户 MUST 能明确批准或驳回方案；驳回 MUST 支持记录理由，
  任务回到可迭代状态。
- **FR-033**: 审批门禁 MUST 由服务端强制；Agent 或自动化组件绕过人工
  审批门禁的尝试 MUST 被拒绝、不产生审批效果，并记录为安全事件。

**取消、失败、恢复与持久化**

- **FR-034**: 用户 MUST 能请求取消正在运行的方案生成；系统 MUST 实际
  执行取消并明确报告真实取消结果（已取消/未能取消/结果已产生等）。
- **FR-035**: 取消后迟到的生成结果 MUST NOT 覆盖已有方案版本、
  MUST NOT 产生隐式批准；MUST 被显式丢弃并记录。
- **FR-036**: 取消、失败、超时历史，核验结果与失败原因 MUST 完整保留，
  MUST NOT 覆盖原始证据。
- **FR-037**: 中断（取消、失败、超时、重启）后的恢复或重试 MUST 具备
  可验证的状态定义与确定行为（见 FR-027 状态机）。
- **FR-038**: AI 生成失败、超时或用户重试时，系统 MUST 展示真实执行状态
  （执行 ID、状态、原因、可重试动作）；重试 MUST NOT 造成重复批准或
  版本覆盖。
- **FR-039**: 任务、需求版本、分析基准记录、方案版本、审批记录、执行与
  失败/取消历史 MUST 持久化且不得覆盖或删除（历史方案与审批事件及其
  原始 Git 基准同样保留）；页面刷新或应用重启后 MUST 可完整恢复。
- **FR-040**: 用户 MUST 能通过网页完成关联、需求、生成、审核、批准
  全流程，无需命令行或复制提示词。

**完整性核验与恢复**

- **FR-045**: 恢复后的补充核验 MUST 基于可信的生成前基准、原分析快照、
  执行记录及足够的权限隔离证据；证据不足以证明完整性或无法确认原生成
  结果已完整完成时，MUST NOT 仅凭恢复后的文件哈希一致判定核验通过，
  MUST 保持「未确认」或标记核验失败并要求重新生成。
- **FR-046**: 系统 MUST 区分「生成执行状态」「完整性核验状态」
  「人工审批状态」三种状态；完整性核验成功 MUST NOT 自动等同于人工批准。
- **FR-047**: 已取消、失败或超时且未产生可信完整结果的生成任务，
  MUST NOT 仅通过事后补充核验恢复为成功方案。
- **FR-048**: 原绑定 Commit 不可访问、已丢失或无法验证其身份时，
  系统 MUST 标记基准不可用，阻止依赖该基准的生成与新审批；
  MUST NOT 自动回退到当前 HEAD。

**外部调用费用与限额信息**

- **FR-050**: 系统 MUST 展示外部 AI 调用中实际可获得的失败原因、限额、
  Token 用量及费用信息；V1.1 MUST NOT 建设完整用量统计面板
  （历史费用汇总、费用图表、预算管理或复杂成本监控均不在范围）。
- **FR-051**: 费用与用量信息 MUST 区分三类：服务商返回的实际用量或费用、
  根据可用数据计算的估算费用、无法获得的费用信息；无法获取时 MUST
  明确标注未知或不可用，MUST NOT 编造金额，MUST NOT 默认视为免费。
- **FR-052**: API 认证方式、计费条件、调用限制及费用获取能力 MUST 在
  技术规划阶段通过受控可行性测试验证。

**安全与权限**

- **FR-041**: 关键执行操作 MUST 受真实权限边界约束；Agent/AI MUST NOT
  拥有批准方案或写入审批数据的能力。
- **FR-042**: 敏感信息（密钥、令牌、个人数据）MUST NOT 进入日志或方案明文；
  调用日志、错误提示与费用信息 MUST NOT 泄露 API Key、Token 等敏感凭据。
- **FR-043**: 恶意仓库内容诱导越权写文件、执行业务代码/构建脚本/测试脚本、
  绕过审批门禁或自动加载不可信规则成功时，MUST 作为阻断级缺陷处理。
- **FR-044**: 权限、隔离与完整性检查的具体技术实现 MUST 留待技术规划
  阶段决策；本规格 MUST NOT 锁定特定 SDK、隔离工具或执行框架。

**技术选型边界（治理约束引用，非本规格决策事项）**

- 遵守已批准路线：后端 Python + FastAPI + Pydantic，前端 Vue 3 +
  TypeScript + Vite，测试 pytest / Vitest（见宪章与 AGENTS.md）。
- Claude Agent SDK、CLI 接入、数据库与 AgentAdapter 实现方案 MUST 留待
  技术规划阶段做可行性验证与 ADR 比较；MUST NOT 提前指定 Claude Agent SDK
  为唯一方案（与 FR-024 一致）。
- MUST NOT 直接 Fork OpenHands 或 Dify；MUST NOT 自动将 LangGraph 加入依赖。

### Key Entities

- **Git 仓库关联**: 用户授权的本地目标仓库，含经配置注入的路径、
  仓库关联身份、分支、绑定基准完整 commit SHA、工作区状态（干净/脏）。
- **开发任务**: 用户的开发需求载体，含当前需求版本引用、当前状态、
  与仓库关联的关系；需求修改通过需求版本体现。
- **需求版本**: 任务需求描述的不可变存档版本；仅在用户正式保存并提交
  修改时创建，草稿变化不产生版本；历史版本永久保留。
- **分析基准**: 一次分析所锚定的完整 commit SHA 与工作区处理决定，
  是方案与审批的不可变引用；分析仅针对该 commit 源码快照。
- **技术方案版本**: AI 生成的方案内容（含证据依据），带版本号、内容摘要、
  生成执行引用；构成版本链；每次正式内容修改产生新版本。
- **修改意见**: 用户对某方案版本的反馈，驱动生成新版本。
- **审批事件**: 对某方案版本的批准/驳回决定记录，绑定需求版本、
  仓库关联身份、完整 commit SHA、方案版本与内容摘要；事件不可变。
- **审批有效性判定**: 基于当前需求版本、分析基准与方案版本对既有审批
  事件的独立有效性结论；变更即失效，历史事件不改写。
- **生成执行记录**: 每次方案生成的真实执行状态（执行 ID、
  运行中/已完成/已失败/超时/已取消/迟到结果已丢弃等状态、原因、
  完整性核对证据）；与完整性核验状态、人工审批状态相互独立。
- **完整性核验状态**: 生成结果只读性证据的核验结论
 （已验证/未确认/核验失败），与生成执行状态、人工审批状态分离；
  「未确认」不可作为审批准入依据。

## Assumptions

- V1.1 为单用户、本地部署场景；示例项目由用户自行提供并授权访问。
- "单任务"指单轮最小闭环场景；系统保留多条历史任务（见 FR-008）。
- 审批一致性采用 R1 审核裁定规则：任何正式方案内容修改均产生新版本
  且不继承审批（不存在"仅措辞修改可免审"的例外，判定权不在 Agent）。
- 需求版本语义已由澄清裁定（正式保存→不可变新版本→重新审批）；
  版本的存储与编号机制属技术规划。
- AI 能力的认证与计费由部署环境准备；产品仅展示实际可获得的失败原因、
  限额、Token 用量与费用（区分实际/估算/未知三类），不管理账单、
  不建用量面板（FR-050~FR-052）；认证与计费能力待技术规划受控验证。
- 出站授权语义已由澄清裁定（默认排除+最小必要+知情确认+可审计+不扩大
  范围+可复用可撤销）；敏感排除规则不作为绝对安全保证；
  交互与存储实现属技术规划（FR-049）。
- 分析环境的隔离方式（快照副本、工作区、进程隔离等）属技术规划决策，
  规格只约束效果（FR-010~FR-013）；Git 快照保存、对象保留与工作区
  隔离的具体实现方式同样留待技术规划。
- 技术选型边界引用已批准的治理约束（宪章 v1.2.0、AGENTS.md），
  不构成新的选型决策。
